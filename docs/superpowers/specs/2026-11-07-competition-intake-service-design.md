# Competition intake service and portfolio generation

The user requested a separate competition service that stores participant preferences, with portfolio-builder reading them to generate portfolios. The user specified one initial generation following SQS intake, then the existing scheduled cadence.

## Boundaries

`services/competition` consumes the existing settings queue, validates theme codes, canonicalizes free text, freezes participant settings, and commits them before acknowledging SQS. It owns intake settings and imports no builder code. Keep the intake transaction and idempotency unchanged.

Portfolio-builder owns generation jobs, retry budgets, portfolio links, prompts, briefing, explanations, and portfolio persistence. A `portfolio-builder-worker` entry point polls the database for participants without a ready portfolio, so committed intake creates initial work even if a process dies after commit. Ready participants are not regenerated by this worker. No additional queue or service-to-service imports are needed.

The existing scheduled builder generates subsequent rounds. A daily participant must generate at most one new portfolio per KST trading date, including a retry/resume of that round. The latest failed explanation remains a resume of the existing portfolio, not a new generation. Shared generation and per-participant budgets keep their existing concurrency guard.

## Pending Backend contract

The Backend's current account snapshot has no participant/account mapping. The proposed contract adds participant_id (explicit null for common accounts, positive integer for participant accounts) to every account. User confirmation is pending. Participant rebalancing and filtering daily generation to active participant accounts cannot be enabled against the current response. Neither account name nor user ID may substitute for that mapping. Lifecycle/report fanout remains tracked in #501.

Initial generation does not require an active account: the portfolio may need to be ready before the competition starts. Recurring generation must stop for participants absent from the active account snapshot. Rebalancer selection must also match the participant's stored user_id. A missing or unready portfolio never falls back to another participant or to the common portfolio.

## Compatibility

Keep the settings request body, participant IDs, canonical hash representation, database tables and lock ordering. Services may define separate read/write DTOs for the datastore contract. Move intake modules rather than introduce a builder library dependency into competition. Do not mix the dependency-extras PR #513 into this change.

Separate participant-specific submission schema and atomic participant linkage from common submission. Keep shared holdings/exits normalization and evidence validation. A participant link must commit in the same transaction as its portfolio.

## Verification

Preserve intake validation and idempotency tests, participant retry and concurrent claim tests, common/participant portfolio isolation, briefing quoting, mandatory disclosure/technical evidence, and atomic linking. Verify initial worker does not regenerate ready participants. Verify independent service images and no cross-service imports. Test scheduled date and account selection once the mapping contract is confirmed.
